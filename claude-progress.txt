## This session: M2-02 — hmac.compare_digest for the static-bearer token check

Second feature in the M2/OAuth milestone, first `blocked`-free `passes: false`
after M2-01. Landed in commit `fb84b63`.

**What was actually wrong:** `trading_mcp/server.py`'s `_build_auth()` built a
`fastmcp.server.auth.providers.jwt.StaticTokenVerifier`. Its `verify_token()`
does `self.tokens.get(token)` — a plain dict lookup. CPython resolves a hash
collision in that lookup with `str.__eq__`, which short-circuits on the first
differing byte, so it is not constant-time. Grepped `trading_mcp/` for a literal
`==` against a token/secret first (feature's own step 1) and found none — the
timing leak was in the *library's* comparison, reached only through the dict
lookup, not in this repo's source. Fixed at the point this repo controls: swap
in a verifier that does the comparison itself with `hmac.compare_digest`.

**What was built:**
- `trading_mcp/auth.py` (new) — `HmacStaticTokenVerifier(TokenVerifier)`, a
  drop-in replacement for the stock class: same constructor shape (`tokens`,
  `required_scopes`), same `AccessToken` result, same expiry/scope checks. Its
  `verify_token()` calls `hmac.compare_digest(token, candidate)` against every
  configured token (a single-operator token set is tiny — usually one entry —
  so iterating all of them costs nothing and keeps timing independent of
  which, or whether any, token matched).
- `trading_mcp/server.py` — `_build_auth()` now constructs
  `HmacStaticTokenVerifier` instead of `fastmcp.server.auth.StaticTokenVerifier`.
  No behavioural change to what gets accepted/rejected, only how the
  comparison is done.
- `tests/test_trading_mcp.py` — 4 new tests: `_build_auth()` returns the hmac
  verifier specifically (not just "truthy", so a revert back to the stock
  class would be caught even though both accept the same tokens); a
  source-level pin (`inspect.getsource` on `verify_token`) asserting
  `"hmac.compare_digest"` appears and `.get(token)` does NOT — mirrors
  `test_notify.py`'s grep-shaped pins, modeled explicitly on that pattern per
  CLAUDE.md's "Tests" section; a behavioural spy that monkeypatches
  `auth_mod.hmac.compare_digest` and asserts it is actually invoked on both
  the accept path and the reject path (not just present in source but dead
  code); and a missing-required-scope rejection case for coverage of the one
  branch the M2-01 ASGI tests don't exercise directly.

**Verified:** `pytest -q tests/test_trading_mcp.py` → 33 passed (29 + 4 new).
Full suite `pytest -q` → **580 passed** (576 + 4, satisfies app_spec.txt §7
DoD #2's "strictly greater than 570"). Confirmed the one pre-existing

## Gotchas discovered this session (not previously documented)

- **`fastmcp.server.auth.providers.jwt.StaticTokenVerifier` is not
  constant-time**, and this is a library property, not something this repo's
  own `==` grep would ever catch — the comparison lives inside `dict.get`,
  several frames past any code this repo wrote. A rule like "grep for `==`
  against a token" needs a companion "and check what the library you're
  calling actually does with it," or it can pass clean while the underlying
  behaviour is still wrong. Worth remembering for M2-03/M2-04 too: whatever
  OAuth library or hand-rolled AS logic gets added there needs the same
  scrutiny of its comparison primitives, not just its opcode-level absence of
  `==`.
- `git stash` / `git stash pop` is a clean way to A/B a warning or failure
  against "does this predate my change" without a second checkout — used here
  to confirm the one pytest warning in the suite is pre-existing.
- Command substitution (`$(...)`) in a `git commit -m "$(cat <<EOF ... EOF)"`
  is blocked by this harness's bash policy ("hides commands from validation").
  Workaround: write the message to a plain file with the `Write` tool (not
  under `.git/` — that path is treated as sensitive and the harness refuses
  to write there) and `git commit -F <path>`.

## M0-08: process-independence proof (trading_mcp.server survives vesper.graph/langgraph being unimportable)

**What it verifies.** `trading_mcp/vesper_tools.py` was already repointed at
`core/` for every stateful tool by M0-06/M0-07 -- this feature adds the
mechanical proof that pays off. New test in `tests/test_trading_mcp.py`:
`test_process_independence_server_survives_vesper_graph_import_failure`.
Runs as a subprocess (fresh interpreter, `subprocess.run([sys.executable,
"-c", script], ...)`), same reasoning as the sibling
`test_calling_every_vesper_tool_never_imports_execution_guard` probe just
above it in the file -- other test modules in the same pytest session have
already imported `vesper.graph`/`langgraph` for real by the time this test
runs, so poisoning `sys.modules` in-process would be a no-op; only a fresh
interpreter makes the poison bite. The script sets
`sys.modules["vesper.graph"] = None`, `sys.modules["langgraph"] = None`, and
blanks every already-cached `langgraph.*` submodule the same way, all
*before* `trading_mcp.server` is ever imported -- Python raises ImportError
for any `import` statement naming a module whose `sys.modules` entry is
`None`. Then: imports `trading_mcp.server` (must succeed), confirms
`srv.mcp.name == "trading-agent"` and all 60 tools list via
`mcp.list_tools()`, then calls `get_halt_status`, `list_pending_proposals`
(the "list_pending_approvals" the feature description names informally --
the actual registered tool name, confirmed against
`test_vesper_tools_registers_exactly_the_documented_thirteen`'s list),
`get_audit_trail`, and `get_position_monitor_status` (the
position-monitor-preview tool) through a `_CollectingMCP`-style stand-in,
same pattern the rest of the file already uses.

**Turned out empty in this repo already, by construction.** Grepped the
whole reachable import graph from `trading_mcp/server.py` for `vesper.graph`
/ `import langgraph` / `from langgraph` before writing the test: the only
hits anywhere in the repo are `vesper.py`, `vesper/graph.py`,
`vesper/runner.py`, `vesper/nodes/human_gate.py` (none reachable from
`trading_mcp/`) and one function-local `from langgraph.types import
Command` inside `core/approval_registry.py`'s `submit_decision()` method --

`trading_mcp.server` needs.

**One real gotcha this test surfaced: don't let `trading_mcp.server`'s
`load_dotenv()` load this developer's real Webull credentials into the
probe subprocess.** `trading_mcp/server.py` calls `load_dotenv()` at import
time, and this repo's `.env` genuinely has `WEBULL_APP_KEY`/`WEBULL_SECRET`
etc. set (confirmed by name only, per the name-only-check rule -- never by
value). `python-dotenv`'s `load_dotenv(override=False)` (the default) never
overwrites an already-set env var, so the script presets `WEBULL_KEY`,
`WEBULL_APP_KEY`, `WEBULL_SECRET`, `WEBULL_APP_SECRET` to `""` *before*
importing `trading_mcp.server` -- `core/wb.py`'s `credentials()` then raises
`WebullError` synchronously on the empty key/secret, before any network I/O
could happen, so `get_position_monitor_status`'s live-broker poll can never
reach out to the real account. This mirrors what every existing
Webull-touching test in this file already does deliberately
(`test_get_account_state_degrades_when_webull_unconfigured` monkeypatches
`Webull` itself to raise the same way) -- I nearly missed it because the
subprocess pattern this test borrows from
(`test_calling_every_vesper_tool_never_imports_execution_guard`) never
imports `trading_mcp.server` itself (only `trading_mcp.vesper_tools`
directly), so it never triggers `load_dotenv()` and had no need for this
guard.

**Second gotcha, environment-specific, not a code bug: the webull SDK
package itself isn't installed in `.venv`** (this repo's test env stubs it
via `tests/conftest.py`'s `sys.modules` fakes for in-process pytest runs,
but a subprocess spawned with `subprocess.run` doesn't inherit that stub).
`core/position_preview.py`'s `poll_webull_positions()` catches the resulting
`ModuleNotFoundError` internally and logs a warning, returning an *empty
position list* rather than propagating -- so `get_position_monitor_status`
came back `available: true, position_count: 0` in this environment, not
`available: false` as I first assumed reading the feature description's
"available:false with a reason where a genuine vesper-only surface
remains" clause literally. Both outcomes are the same thing the feature
actually cares about (a normal dict shape, no unhandled exception) --
whichever one shows up depends on whether the real webull package happens
to be importable, which is an environment detail, not this feature's
concern. The test now asserts `isinstance(pm["available"], bool)` and, only
conditionally, `pm["reason"]` when `available` is `False` -- asserting a
literal `available is False` here would have been exactly the "verifying
two documents agree with each other, not either against the code" mistake
the standing warning calls out, since the feature description's prose
guessed at a specific runtime outcome that the actual code (a
broad-except-and-degrade-to-empty pattern) doesn't guarantee.
