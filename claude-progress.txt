## This session: M2-02 — hmac.compare_digest for the static-bearer token check

Second feature in the M2/OAuth milestone, first `blocked`-free `passes: false`
after M2-01. Landed in commit `fb84b63`.

**What was actually wrong:** `trading_mcp/server.py`'s `_build_auth()` built a
`fastmcp.server.auth.providers.jwt.StaticTokenVerifier`. Its `verify_token()`
does `self.tokens.get(token)` — a plain dict lookup. CPython resolves a hash
collision in that lookup with `str.__eq__`, which short-circuits on the first
differing byte, so it is not constant-time. Grepped `trading_mcp/` for a literal
`==` against a token/secret first (feature's own step 1) and found none — the
timing leak was in the *library's* comparison, reached only through the dict
lookup, not in this repo's source. Fixed at the point this repo controls: swap
in a verifier that does the comparison itself with `hmac.compare_digest`.

**What was built:**
- `trading_mcp/auth.py` (new) — `HmacStaticTokenVerifier(TokenVerifier)`, a
  drop-in replacement for the stock class: same constructor shape (`tokens`,
  `required_scopes`), same `AccessToken` result, same expiry/scope checks. Its
  `verify_token()` calls `hmac.compare_digest(token, candidate)` against every
  configured token (a single-operator token set is tiny — usually one entry —
  so iterating all of them costs nothing and keeps timing independent of
  which, or whether any, token matched).
- `trading_mcp/server.py` — `_build_auth()` now constructs
  `HmacStaticTokenVerifier` instead of `fastmcp.server.auth.StaticTokenVerifier`.
  No behavioural change to what gets accepted/rejected, only how the
  comparison is done.
- `tests/test_trading_mcp.py` — 4 new tests: `_build_auth()` returns the hmac
  verifier specifically (not just "truthy", so a revert back to the stock
  class would be caught even though both accept the same tokens); a
  source-level pin (`inspect.getsource` on `verify_token`) asserting
  `"hmac.compare_digest"` appears and `.get(token)` does NOT — mirrors
  `test_notify.py`'s grep-shaped pins, modeled explicitly on that pattern per
  CLAUDE.md's "Tests" section; a behavioural spy that monkeypatches
  `auth_mod.hmac.compare_digest` and asserts it is actually invoked on both
  the accept path and the reject path (not just present in source but dead
  code); and a missing-required-scope rejection case for coverage of the one
  branch the M2-01 ASGI tests don't exercise directly.

**Verified:** `pytest -q tests/test_trading_mcp.py` → 33 passed (29 + 4 new).
Full suite `pytest -q` → **580 passed** (576 + 4, satisfies app_spec.txt §7
DoD #2's "strictly greater than 570"). Confirmed the one pre-existing

## Gotchas discovered this session (not previously documented)

- **`fastmcp.server.auth.providers.jwt.StaticTokenVerifier` is not
  constant-time**, and this is a library property, not something this repo's
  own `==` grep would ever catch — the comparison lives inside `dict.get`,
  several frames past any code this repo wrote. A rule like "grep for `==`
  against a token" needs a companion "and check what the library you're
  calling actually does with it," or it can pass clean while the underlying
  behaviour is still wrong. Worth remembering for M2-03/M2-04 too: whatever
  OAuth library or hand-rolled AS logic gets added there needs the same
  scrutiny of its comparison primitives, not just its opcode-level absence of
  `==`.
- `git stash` / `git stash pop` is a clean way to A/B a warning or failure
  against "does this predate my change" without a second checkout — used here
  to confirm the one pytest warning in the suite is pre-existing.
- Command substitution (`$(...)`) in a `git commit -m "$(cat <<EOF ... EOF)"`
  is blocked by this harness's bash policy ("hides commands from validation").
  Workaround: write the message to a plain file with the `Write` tool (not
  under `.git/` — that path is treated as sensitive and the harness refuses
  to write there) and `git commit -F <path>`.

## M2-06 — One authorization-decision function; OAuth cannot escalate scope

**Read first, per the feature's own step 2:** `docs/SUPERMCP_SWAGGER_AND_AUTH_PLAN.md` (no
`authorize()` bug material there -- it's the swagger-doc design plan, not a postmortem) and
`docs/HANDOFF_2026-09-01.md` (names the bug in passing: "`authorize()` no longer force-grants
admin on every OAuth handshake"). The actual postmortem with the mechanism is
`docs/AUTH_TRADE_SCOPE_LOCKDOWN.md`: supermcp's `POST /login` handed back
`config.SUPERMCP_TOKEN` (the admin credential) for a match against the *shared dashboard
password*, because a newly-landed RBAC commit had given that token `['read','trade','admin']`
scope and nobody re-checked what `/login`'s password branch was still handing out. The
`authorize()`-specific phrasing in the handoff is the same failure shape one level up: an
OAuth handshake reaching a grant-issuing function was itself treated as sufficient
authorization, with no check of what was actually requested or registered.

**Step 1 -- confirmed there is exactly one convergence function, empirically, not by
inspection.** Traced it in `fastmcp`/`mcp` SDK source
(`.venv/.../fastmcp/server/auth/auth.py` `AuthProvider.get_middleware()`,
`.venv/.../mcp/server/auth/middleware/bearer_auth.py` `BearerAuthBackend`): the ASGI app gets
exactly ONE `AuthenticationMiddleware(backend=BearerAuthBackend(self))`, where `self` is
whatever single object `trading_mcp/server.py::_build_auth()` returns -- our `MultiAuth`
instance when OAuth is configured. `BearerAuthBackend.authenticate()` calls
`self.token_verifier.verify_token(token)` for every request regardless of which credential
shape it is, so both the static bearer and any OAuth-minted token are decided by the identical
bound `MultiAuth.verify_token()` method constructed once in `_build_auth()`. There is no
second backend, no second middleware, no per-credential-type branch anywhere in the request
path -- confirmed by reading the actual middleware wiring, not by trusting the existing
docstring's claim.

New test `test_bearer_and_oauth_paths_converge_on_one_verify_token`
(`tests/test_trading_mcp.py`) proves this behaviourally: it monkeypatches the bound
`verify_token` method on the exact `MultiAuth` instance the live app uses, drives one real
request with the static bearer token and one with a freshly-minted OAuth access token (full
register -> gate -> authorize -> token round trip through the real ASGI app), and asserts the
SAME patched function observed both token strings. A regression that added a second,
un-patched auth path (the supermcp shape) would leave one of those two `assert ... in
seen_tokens` failing even though both requests still returned 200.

**Step 3/escalation -- three tests, at three different layers, since a fix at only one layer
would leave the others silently relying on it:**

- `test_dcr_registration_rejects_scope_beyond_valid_scopes` -- registration itself
  (`ClientRegistrationOptions(valid_scopes=["read"])`, enforced by the SDK's
  `RegistrationHandler`) is the first checkpoint; a client can never even register for a scope
  beyond "read" (the only scope this server issues today).
- `test_authorize_request_for_unregistered_scope_never_issues_a_code` -- end-to-end HTTP:
  requesting `scope=admin` at `/authorize` (past the operator-key gate, with a registered
  client) gets a 302 redirect carrying `error=invalid_scope`, never a `code` -- the mcp SDK's
  `AuthorizationHandler` validates the requested scope against the client's registration
  before `SingleOperatorOAuthProvider.authorize()` is ever reached.
- `test_authorize_itself_filters_scope_beyond_client_registration` -- the important one,
  because it's the exact function shape that broke in supermcp: calls
  `SingleOperatorOAuthProvider.authorize()` **directly**, bypassing the SDK's upstream check
  entirely, with `AuthorizationParams.scopes=["read", "admin"]` against a client registered
  for `scope="read"`. Confirms the issued `AuthorizationCode.scopes == ["read"]` and that the
  token exchanged from it inherits exactly that -- proving `authorize()`'s own
  `scopes_list = [s for s in scopes_list if s in allowed]` filter is what stops the
  escalation, not merely the SDK's front-door validation (which a future refactor could route
  around, e.g. a second internal caller of `authorize()`).
- `test_refresh_token_cannot_escalate_scope_beyond_original_grant` -- the fourth checkpoint,
  covering a path the M2-05 report didn't touch: `exchange_refresh_token()`'s
  `requested.issubset(original)` check refuses (`TokenError`) a refresh that asks for `read`
  when the original grant carried no scopes at all.

**No behavioural code changes** -- every one of these checkpoints (registration validation,
authorize()'s intersection filter, the SDK's upstream scope check, the refresh-token subset
check) was already correct from M2-03. This feature is: read the supermcp postmortems as
instructed, confirm the convergence property against actual SDK wiring rather than trusting
the docstring, and add tests that would catch a regression at each of the four places listed
above -- plus write the reasoning into the code so the next change to `authorize()` or
`_build_auth()` sees why the shape must not change, per the feature's step 4.

**Comments added, not just tests:** `trading_mcp/server.py::_build_auth()`'s docstring now
explains the middleware-level mechanism that makes convergence true and names the specific
supermcp failure it must not regress into. `trading_mcp/oauth_provider.py::authorize()` gets
an inline comment directly above the scope-filtering lines, since -- per this feature's own
framing -- that is "the exact shape that went wrong once already": it names what's
attacker-controlled (`params.scopes`), what's trusted (`client.scope`, itself already bounded
at registration), why the SDK's upstream check is a second layer and not a substitute, and
which tests pin it.

layer, error only at the JSON-RPC/application layer. That's the mechanical difference between
"not found" and "permission denied" this feature asks to be proven, not asserted.

M2-08 -- static bearer fallback keeps working unchanged after OAuth lands;

===============================================================================

**Outcome, checked against source, not asserted.** Read `trading_mcp/server.py`'s
`_build_auth()` and the `__main__` startup guard before touching anything. Both halves of
the claim were already true in the shipped code from M2-04/M2-06:

- `_build_auth()` only ever returns `None` (no token), a bare `HmacStaticTokenVerifier`
  (token set, no `MCP_PUBLIC_URL`), or a `MultiAuth(server=oauth, verifiers=[bearer])`
  (both set) -- there is no fourth branch where mounting OAuth drops the bearer verifier
  from the composition.
- The `MCP_TRANSPORT=http` + no-`TRADING_AGENT_TOKEN` guard at the bottom of the module
  checks `os.environ.get("TRADING_AGENT_TOKEN")` alone, before `_build_oauth_provider()`
  is even reached -- `MCP_PUBLIC_URL` being set can't substitute for it.

So this feature was a coverage gap, not a code bug: the M2-01-era characterization tests
(`test_http_request_with_no_credential_is_rejected`, `test_http_request_with_valid_bearer_is_
accepted`, `test_http_transport_refuses_to_start_without_token`) never set `MCP_PUBLIC_URL`,
so "still pass unchanged" was true only by never exercising the OAuth-mounted case at all --
nothing proved the SAME three behaviours hold once `_build_auth()` returns the composed
`MultiAuth` instead of the bare verifier.
